# CP-OPS-004 S01

### S01 — the base a trunk push is compared against — **COMPLETE**

#### Plan

Replace the kept `CAIRN_BASE_REF` expression with the one the release
installs, so a push to the trunk is judged against the commit it replaced
rather than against itself. Nothing else changes.

#### Work

```cairn-unit
step: S01
unit: 01
type: implementation
verified: cairn-check
```

- `.github/workflows/cairn.yml`: `origin/${{ github.base_ref || 'master' }}`
  becomes the release's three-way expression — the target branch on a request,
  `github.event.before` on a push to the trunk, `origin/master` on a push to a
  path branch.
- the comment names the three events and what each base must be. It carries no
  path history: the first draft put this unit's causal story in the workflow,
  and the story was wrong. A shipped file is the worst place to be wrong.
- **only the trunk-push arm changes behaviour.** On a request and on a
  path-branch push the old expression already produced the same base; two of
  the three were right.

#### Why it was never caught, corrected

The first draft of this record said the protocol check had never run on a push
to the trunk, and cited `gh run view 35603269125` — `validator self-test →
failure`, `protocol check → skipped` — as proof. That evidence is real and it
proves nothing of the sort: it covers only the pushes after the 1.1 adoption.
A reader checked the rest and the claim is false. `gh run view 33622357741`
shows the `protocol check` step succeeding on the trunk at `46bdd11`, and it is
not alone: `gh run list --branch master --workflow cairn.yml` counts **13**
green trunk runs, and the stale base has been in that step since the workflow
was introduced at `92f25cb`, so every one of them ran it.

The true cause is worse, and it is the better argument for this unit:

```bash
git show 46bdd11:tools/cairn-check.mjs | grep -c "already contains this commit"   # → 0
```

**The `comparison` rule did not exist in the pre-1.1 checker.** It arrived with
the 1.1 adoption. So the stale base was exercised on the trunk thirteen times
and reported green every time — with an empty comparison, every
changed-file rule narrowed to the working tree, the job judging nothing and
saying so to nobody. What CP-OPS-003 S01 changed is not whether the check ran;
it is that the check could finally speak, and the first thing it said was that
it had been judging an empty set.

The run that said it, `3ab9670`, abridged to the finding — the full output
carries the binding and profile lines and an `INCONCLUSIVE` header:

```text
cairn-check — profile ci, branch master, base origin/master (flag), 0 changed file(s)
  […]
  [comparison] the base given already contains this commit, so the comparison
  is empty and every changed-file rule was narrowed to the working tree —
  provide a base that predates what you are judging: the target branch for a
  request, and for a push to the trunk the commit it replaced
FAILED — 0 failed, 1 inconclusive
```

The rule states its own repair exactly. Nothing had ever been able to ask it.

#### What this says about CP-OPS-003's closure

CP-OPS-003's outcome 1 reads *a push to `master` and to a `path/**` branch both
go green*. Its closing review claimed it, citing the branch's CI. The branch
half was observed; **the trunk half never was**, and could not have been. The
path closed on a claim its writer reasoned to rather than measured — the same
defect that unit's own reviews caught five times in figures and citations, one
level up, in an outcome.

The third outcome of this path exists to record that in the journal rather than
let the correction be silent.
