The last S08 Part 2 item. The conformance matrix is the mechanism by which an
unenforced requirement is distinguished from an unsound gate — and it was
maintained entirely by hand, which is the one condition under which it cannot
perform that job.

**Generating the rows is not possible and is not claimed.** A row is a judgement
about the protocol in prose; a validator cannot write one. What was silently
hand-maintained and CAN be generated is the **linkage**: which rule stands behind
which stated requirement, and which rules stand behind none. A row claiming
`implemented` with no rule behind it, and a rule enforcing nothing the matrix
states, are both invisible from a green run.

`RULE_CONFORMANCE` maps thirty-one rules to the exact first column of the row
they enforce. `RULES_OUTSIDE_CONFORMANCE` declares the other eight with a reason:
they keep the documentation plane coherent — links resolve, vocabulary is
accounted for, generated files are regenerated, notes stay current — rather than
enforcing a stated protocol capability. Mapping them to a row that does not mean
them would make the table look complete while saying something false.

Four conditions fail the build: a rule in neither map, a rule in both, a mapped
row title that no longer appears in the matrix, and a mapped rule the checker
does not implement.

## The fixture caught the check reading its own output

The adversarial test for this unit renames a matrix row and requires the build to
break. It failed — because the region searched for row titles ran to the next
`##` heading, which now includes the GENERATED linkage table. Renaming the row
left its old title sitting in the generator's own output, so the check found it
and reported nothing.

That is precisely the failure mode this path is named for: a predicate satisfied
by the artefact it produces. It was written and caught within the same unit only
because the fixture demanded a rejection rather than asserting `OK`. The searched
region now stops at the generated block.
