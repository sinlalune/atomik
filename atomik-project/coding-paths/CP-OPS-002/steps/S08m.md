# CP-OPS-002 S08m

### S08m — A fifth rule dated a record by the commit that moved it — **COMPLETE**

```cairn-unit
step: S08m
unit: 31
type: repair
verified: cairn-check, cairn-check:test, cairn-spec:build, typecheck, test, build
```

Found by running the gate after [S08l](./S08l.md) landed, which is the only place
it could have been found: before the commit the renames were staged and the rule
was quiet, and after it the advisory count went from 14 to 31.

Nineteen `record-date` advisories, each saying a relocated record *"is dated
2026-08-25 and was written on 2026-09-01, 7 days apart"*. Every one of them false
in the same way. `addedRecordDates` asked

```text
git log --diff-filter=A -1 -- <file>      when did this PATH first appear
```

and used the answer for *when this record was written*. For a record that has
never moved the two coincide, which is why the substitution survived; for the
twenty-three records S08l relocated they are seven days apart, and the rule
accused the records of the migration's own date.

That is the same substitution S08l repaired in `registration`, `transition` and
`record-integrity` — **a name standing in for the fact it resembles** — in a
quieter voice, in an advisory nobody would have had to act on. The fix is
`--follow`, which is Git's own answer to "and before it was called that":

```text
steps/S00.md    --follow 2026-08-25   without 2026-09-01   relocated
steps/S08l.md   --follow 2026-09-01   without 2026-09-01   genuinely new
steps/S08a.md   --follow 2026-09-01   without 2026-09-01   new file, 1 day drift
```

The rule keeps its teeth: `S08a.md` is a record cut out of the live file today
and carrying yesterday's date, and it still reports — inside tolerance, but
reported by the same code path. Only the records with a rename behind them stop
being accused of a date they never claimed.

Advisories: 31 → 13, and twelve of the thirteen are the ones that were there
before S08l. The thirteenth is this unit's own retention ref, written after the
commit that declares it.
