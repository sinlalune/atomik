## The defect

`resolveBranch` trusted `GITHUB_HEAD_REF` and `GITHUB_REF_NAME` before Git.
That was the S08 repair for a detached `pull_request` checkout, and it is
correct for the repository the host checked out. The fixture suite builds small
repositories under a temporary directory and runs the real checker inside them;
in CI those runs inherited `GITHUB_REF_NAME=path/cp-ops-002` and every fixture
was judged as that branch, which none of them had: `branch-path` fired on the
baseline of every adversarial fixture, the freshly installed repository "failed
its own gate", and one parity test asserted a rule that never got to run.

It is the same shape this path has named since its audit, one level out: the
environment is a proxy for "which branch is this tree on", and it is truthful
only for the tree it describes. The property it broke is the one the suite
claims to prove — gate parity — and the suite could not see it because the
suite itself was the thing that lacked parity.

## What changed

- **`tools/cairn-check.mjs`.** `hostDescribes(env, root)`: a host variable is
  trusted when the host names no workspace, or names the repository under
  check (`GITHUB_WORKSPACE` against the resolved root, real paths compared).
  `resolveBranch` takes the root and applies it; the call site passes `REPO`.
- **`tools/cairn-check.test.mjs`.** Three cases: a workspace elsewhere falls
  through to Git; the workspace itself still wins over a detached checkout; a
  host naming a branch and no workspace is trusted as before.
- **`tools/cairn-fixture.test.mjs`.** `checkWithEnv()` makes the environment a
  parameter, and a parity fixture reproduces the CI failure: the real checker
  inside a fixture repository, under the host's exact variables, must reach the
  local verdict and must not fire `branch-path`. It failed on the old code and
  passes on the new; the whole suite was also run under those variables.
- **`concepts/gate-parity.md`.** The second break, recorded as the sharper
  worked example. Reader regenerated.
- **Path record.** `status: running`, `subject_commit` removed; the closure
  repeats from here.

## Not done, and said so

- Nothing predicates *reading CI*. The rule that the local and CI verdicts
  agree exists; the rule that someone looks at CI's verdict before calling a
  unit complete does not, and seven pushes went by. It is a candidate advisory
  for the genesis (`ci-unread`: a pushed unit whose remote run is red or
  unknown), recorded in the plan, not added here.
- The product gates were not rerun: no product file changed.

## Correction, same day

The unit above was committed and pushed as `2def1a2` with the derived
running-paths view stale: the status change from `ready` back to `running`
moved the view's line, and the script that ran the gate printed its `FAILED`
and went on to commit. The gate was read and not obeyed — the exact failure

the view is regenerated in this follow-up commit, which is the candidate the
closure binds. Every later gate in this closure is checked by its exit code
before the next command runs.
