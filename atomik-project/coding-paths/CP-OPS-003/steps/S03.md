#### The transport measurement

The plan required establishing what the checker does with this repository's
historical integrations before moving the field. Run twice over the same wide
comparison, `--base 41d661b~1`, changing only `transport.integration`:

```text
manual-git   : 24 findings
pull-request : 23 findings
only under pull-request: 4 × [acceptance] — CP-OPS-001, CP-OPS-002,
                         CP-UI-TYPOGRAPHY, CP-WORKTREE-CLEANUP reach done in a
                         merge object rather than in a commit of their own
```

Four appear and **five disappear** — `[acceptance] missing closing record` for
CP-MVP-008, CP-OPS-001, CP-OPS-002, CP-UI-TYPOGRAPHY and CP-WORKTREE-CLEANUP,
which only `manual-git` requires, because on `pull-request` the request is the
record. That is why 24 becomes 23. So the move costs four blocking findings and
refunds five, all against paths integrated in 2026-08, and either set appears
only in a run whose comparison spans those merges.
No routine run makes that comparison: a path branch is compared with its
merge-base, and a trunk push with the commit it replaced.

It is taken because the declaration was false. The trunk requires a pull
request and `allowed_merge_methods` is `[merge]`, so an accepted candidate
reaches `master` through the forge. The most recent integration already had the
`pull-request` shape — `09f1ca2` records the integration and `46bdd11` is the
forge's merge of request #4 — while the configuration said `manual-git`. The
four findings are the honest price of saying what this repository does.

`transport.registration` stays `manual-git`. It was false on 2026-09-21 morning
and is true now: the bypass actor makes the sequence `cairn-open` ships
executable here. That is also why the binding names the bypass rather than
leaving it as a fact of the forge.
