# CP-OPS-003 S07

### S07 — the post-mortem's own run — **COMPLETE**

#### Plan

Answer a finding on the closing request: the post-mortem step S04 wired
publishes a false sentence on the incident it exists to report. Advances
outcome 5 — a tool that publishes a false reading is not *wired*.

**Candidate `0c24d5cfd3028808b3b75b2744acc1cbfae93cd9` is void.** It was
proposed on the request and this unit changes a file inside it, so closure
repeats on a new candidate. The path never left `running`, and no
administrative commit had been made, so nothing is unwound.

#### The finding

Raised by the request's automated reviewer against
`.github/workflows/cairn.yml`:

> When this step runs after `cairn-check` fails, the workflow run is still
> `in_progress`, but `readRedRuns()` queries the Actions API with
> `status=failure`; the current incident is therefore excluded, so a branch's
> first failing run will publish the false statement *no red run on this
> branch*.

Checked, and true. `tools/cairn-postmortem.mjs:238` asks the forge for
`actions/runs?branch=<b>&status=failure` and reports `total_count`. That
parameter filters by **conclusion**, and a run printing from inside its own
failing job has no conclusion yet. On a branch's first failure the reading
therefore says *no red run on this branch* while the reader is looking at one.

- the comment names the defect, says it is Cairn's and filed, and points at

#### Whose defect, and why it is not repaired here

It is Cairn's, and it is already reported: **observation 7 of the Crumbz update
note**, `feedbacks/2026-09-16-crumbz-update-to-1-1.md`, merged upstream and
open on the 1.2 row — *the post-mortem tool cannot count the run it is running
in*. No new feedback note is filed; a second note arguing a filed observation
is noise in a folder that already cannot say which of its notes has been
treated.

The repair belongs in `readRedRuns`, which is a kit file. This repository
already holds one kit file ahead of its release and pays for it in ADR-023;
forking a second to fix a reporting line would be the expensive answer to a
cheap problem. The host owns the workflow, the workflow knows the run failed,
and one line there makes the reading true.

#### Self-review

- `shrink:` the fix is one `printf` and one `env` line. No flag was added to
  the tool, no wrapper script, no second fork.
- `yagni:` the line does not try to correct the count. It names the run and
  says the reading cannot include it, which is what the host can state
  truthfully without re-implementing the tool's question.
- net: `git diff --numstat` on the workflow, not an eyeball.

#### Review

First read — reader: a fresh context, a subagent of this session, given the
diff and the two criteria and nothing else. It parsed the workflow, extracted
the step's `run:` body and executed it, and confirmed the `status=failure`
claim against GitHub's documented behaviour — *returns workflow runs with the
check run status **or conclusion** that you specify*:

- **the appended line printed two blank lines and sat one column off.** The
  tool's renderer already ends its output with a blank line, and its readings
  start at the column its longest label defines — which the hand-counted
  padding missed by one. **Fixed**, by the reader's own cheaper form: a single
  `printf '  %-21s  %s\n'` that uses the same column the tool uses, drops the
  leading newline and loses a line continuation.
- **`verified: the step's shell run verbatim` overstated what was done.** The
  run was made; its output was not read against the tool's formatting, which is
  exactly where both defects were. **Fixed**, and the line now says the output
  was read. Running a command and not reading it is not verification, and this
  record said it was.
- the sentence presumed a count exists, which is false when the forge is
  unreachable or there is no token — **fixed**, it now says the reading *cannot
  include* this run, which is true either way. Same class of false sentence the
  unit exists to remove, one layer down.
- the self-review's accounting was wrong — twelve lines for eleven, four
  non-comment for three — **fixed**, and it now names the command instead of a
  number.
- four of the eight comment lines duplicated this record's own section —
  **fixed**, six lines, pointing rather than restating.

Second read — reader: a fresh context, a subagent of this session, given only
the diff of those fixes and the same two criteria. It extracted the step's
`run:` body from the YAML, executed it, and read the result with `cat -A`:

- **the alignment was bought for a rendering nobody sees.** `postmortem.txt` is
  posted with `gh pr comment --body-file` as plain markdown, and GitHub
  collapses runs of spaces — the columns exist only in the raw Actions log.
  **Fixed:** the `printf` is a plain `echo`, one line, no continuation.
- **and the padding was a coupling to a kit file.** `renderReadings` computes
  its width as `Math.max(...labels.map(l => l.length))`; 21 is today's value
  only because `administrative commit` is 21 characters. This record called it
  *the same column the tool uses*, which is not what the code does — a
  hardcoded number that happens to match, in the one file this unit argues the
  host does not control. **Both the claim and the coupling are gone.**
- *"so it lands in the tool's own table"* was false in the executed output: the
  renderer closes with its own sentence, so the appended line lands after it.
  **Fixed** — the claim is removed rather than reworded, because the line does
  not need to be in the table to be true.
- the sentence still presumed a reading existed above it, which the step's own
  documented error path breaks: a thrower puts a diagnostic in the file and no
  readings, and the append runs unconditionally. **Fixed**, and both paths were
  executed this time rather than reasoned about.
- four comment lines pointed at files that do not exist in this repository —
  **fixed**, only ADR-023 is named, which is local.
- the reader notes `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY` and `GITHUB_RUN_ID`
  are already in the step's environment, so the `env:` entry is readability
  rather than necessity — **kept**, deliberately: the expression says what the
  line is made of where the line is read.

The lesson of this unit, twice over: the first read caught that the output was
not looked at, and the second caught that looking at it once, for one defect,
is not looking at it.
