Canonical protocol · v1.0

Cairn, from intent to integrated work.

A repository-native protocol for running several bounded coding paths in parallel while keeping every decision, checkpoint, gate, and handoff durable enough to survive the current conversation.

Core invariant

One coding path = one branch = one worktree = one writer.

Read the specification ↓
01 · AcceptOpening checkBound the outcome and record the owner's acceptance.
02 · PublishRegisterPut stable metadata on the trunk before branching.
03 · IsolateExecuteOne worktree, one writer, pushed step checkpoints.
04 · IntegrateSelf-mergeClose, rebase, verify, audit, merge, and clean.
OWNER

Intent and acceptance

Accepts the bounded path before it starts and the delivered result before it merges.

WRITER

One path end to end

Owns its worktree, implementation, tests, documentation, ledger, audit, and self-merge.

CHECKER

Mechanical evidence

Evaluates files, metadata, ancestry, and exit codes; never pretends to make a human judgement.

02

The project model

Put each kind of state in a durable, navigable home

Cairn starts by distinguishing the knowledge that defines a system, the execution state that moves one task forward, and the temporary context of the current conversation.

FoundationWhy a file can be durable without being true:durable state, canonical sources, and generated views
PlaneCanonical homeQuestionLifetime
Knowledgedocs/What should the system be, and why?Durable
Execution stateproject/What is this bounded task changing, and where does it stand?Durable
Ephemeral contextconversation or process memoryWhat is being considered right now?Temporary

Progress, acceptance, decisions, and next actions must be persisted in files. Conversation memory must not be their only home.

Canonical repository shape

The protocol names roles, then cairn.config.json binds those roles to a repository. These are the canonical defaults:

repository/
├── AGENTS.md
├── cairn.config.json
├── src/ …
├── docs/
│   ├── architecture/
│   ├── adr/
│   └── modules/
└── project/

    ├── coding-paths/
    │   ├── index.md
    │   ├── ACTIVE.md          # generated

    │   └── history/
    ├── sessions/
    ├── audits/
    ├── briefs/
    └── log/                  # one file per merge

Four ownership classes

CANONICAL

Edited deliberately

Architecture, ADRs, and module notes change when their represented decision or contract changes.

PATH-OWNED

One active writer

A path and its handoff brief belong to exactly one branch and writer.

GENERATED

Never hand-maintained

Views such as ACTIVE.md are regenerated from canonical inputs.

Namespace rule

Audits, sessions, journal entries, and rolled ledger steps use uniquely named files. Several paths must not append to one shared mutable record.

03

The coding path

One bounded task, fully reconstructible from one durable record

A coding path is not merely a checklist. It binds an accepted outcome to a Git identity, governing documents, execution steps, a live ledger, and an exact next action.

Identity tuple

cairn:
  id: CP-EXAMPLE-001
  status: running
  current_step: S02
  base_commit: a1b2c3d
  branch: path/cp-example-001
  writes:
    - src/example/**
    - docs/modules/example.md

Why base_commit matters

A commit id identifies the entire project snapshot and its ancestry. Recording the trunk tip immediately before registration pins the state against which the path was accepted.

Documentation coverage

Every path classifies relevant documents instead of silently skipping them:

ClassMeaning
RequiredRead before execution.
ConditionalRead when a named trigger occurs.
Deliberately excludedOutside scope, with a reason.

writes: is a signal, not a lock

The declared surfaces reveal likely overlap and allow a final diff-versus-scope review. A root cause is discovered, not fully known in advance. When work widens, the writer records the new surface and governing documentation, then continues.

Ledger and handoff

The work ledger records each executed step, checks, decisions, remote commit, next action, and blockers as the work happens. A handoff brief is a shorter projection refreshed from that ledger. If the brief, path, and Git disagree, Git grounds the correction and the ledger is reconciled.

Reading boundary

When the live path becomes too expensive to read, completed major steps move to history/<id>-SNN.md verbatim. The live file keeps the declaration, index, checkpoint, next action, and blockers.

04

Lifecycle

Five states, two exits, and honest mechanical limits

draft→running→done→archived
running↔blocked · running→archivedabandonment
StatusMeaningMechanical invariant
draftProposed, not accepted.Identity and proposed scope.
runningAccepted, registered, executing in isolation.Branch, base commit, opening record, trunk registration.
blockedWaiting on a named condition.Blocker and route to resume; no active branch obligation.
doneAccepted, rebased, audited, and merged.Closing record.
archivedOff the live portfolio, retained as history.Reason for archival.

archived is the single terminal state. Completed work normally moves done → archived. Abandoned work moves running → archived without claiming the merge represented by done.

Honest limit

A validator normally sees one repository snapshot. It can enforce the invariant of the state declared now; it cannot claim to have observed the transition from yesterday's state.

A resolvable running branch that stays quiet past the configured window receives an advisory notice. Age alone must not fail an unrelated build.

05

Opening a path

Accept first, publish the identity, then diverge

Opening turns an agreed intention into globally visible execution state. The order is load-bearing.

  1. Bound the outcome. Name the major features, definition of done, governing documents, expected writes, and exclusions.
  2. Run the opening check. The owner accepts or amends the path item by item.
  3. Write the opening record. It declares the exact path id and ceremony: opening.
  4. Pin the identity tuple. Set status: running, branch, and the trunk tip immediately before registration.
  5. Regenerate and check. Produce ACTIVE.md from the registered paths and run the local checker.
  6. Publish metadata only. Commit and push the declaration, active view, and opening record to the trunk. No implementation.
  7. Create isolation. Only now create the path branch and worktree from that registration commit.
path: CP-EXAMPLE-001
ceremony: opening

The fields are root-level and the path id is matched exactly. The filename helps a person navigate; declared metadata establishes identity and kind.

Why registration precedes the branch

A checkout cannot scan files that exist only on sibling branches. Publishing the stable identity on the common trunk makes the running portfolio globally visible before private histories diverge.

Registration rule

The commit is metadata-only, not an arbitrary file count. It may repair metadata needed for coherence; it must contain no implementation.

06

Executing a path

One coherent step becomes one remote recovery point

Create the isolated worktree

git worktree add ../repo-cp-example-001 \
  -b path/cp-example-001 main
cd ../repo-cp-example-001

No second writer modifies that filesystem. If the application uses mutable runtime resources, the path also receives its own profile, port, cache, database, or socket.

FoundationBranches isolate committed history; worktrees isolate live files.

One step is one work unit

implementation
  + tests
  + affected architecture/module documentation
  + path ledger checkpoint
  + refreshed handoff brief

The unit should express one reviewable idea and leave the repository at a safe recovery point. Stage explicit files rather than an undifferentiated working tree.

Run gates bare

npm run cairn-check
npm run typecheck && npm test && npm run build

A gate's process exit code is its verdict. Do not pipe the first run through a filter that can replace that status.

FoundationTests, exit codes, continuous integration, blocking, and advisory — from zero

Commit and push form one completion unit

  1. Commit the coherent step on its path branch.
  2. Push the commit immediately to the branch's upstream.
  3. Record that remote commit in the ledger.
  4. Only then report the step complete.

If pushing fails, the honest state is “implemented locally, not complete.”

Every completed, pushed step is a safe session boundary. A fresh session reads the bootloader, active paths, path ledger, and handoff brief; checks them against Git; and begins the recorded next action without an oral recap.

07

Parallel paths

Parallel work, structurally separate; integration, briefly ordered

Cairn removes the permanent integrator by giving each path exclusive ownership and making the merge preconditions mechanical.

FoundationWhy one shared status file can become wrong even when Git merges it cleanly

Avoid shared evolving files

GENERATE

Aggregate views

ACTIVE.md is regenerated from registered path declarations. Writers edit inputs, never the view.

PARTITION

Append-only records

Journal entries, audits, sessions, and rolled steps receive path-specific filenames.

SIGNAL

Expected overlap

writes: reveals likely collision but remains advisory so discovery can widen honestly.

Serialise integration, not work

Paths execute together. When one merges, the next rebases on the new trunk and reruns its gates. The protocol serialises a short integration boundary instead of appointing a person to serialise all work.

08

Closing and self-merge

Human acceptance, current ancestry, green gates, recorded judgement

Closing converts branch-owned execution state into an accepted trunk result. Each condition leaves a durable artifact or an objective verdict.

  1. Closing ceremony. The owner accepts the delivered result in a record declaring ceremony: closing.
  2. Rebase. Replay the path on the current trunk so path HEAD contains the trunk tip.
  3. Quality gates. Run protocol and product checks on that rebased result.
  4. Coherence audit. Review the diff against accepted architecture, ADRs, coverage, and overlapping paths.
  5. Complete the record. Set status: done in the merge unit.
  6. Self-merge. Merge the path into the trunk and push the trunk immediately.
  7. Verify and clean. Prove the remote merge, then remove the exact clean secondary worktree from another checkout.

The rebase gate

current trunk tip is an ancestor of path HEAD

A rebase produces new commit ids. When the old path commits were already pushed, use --force-with-lease, record the pre- and post-rebase heads, and never use blind --force.

The coherence audit

A reviewer or agent produces the judgement. The checker verifies only that a filled record is bound to the path's own work. Its verdict remains advisory because architecture cannot be reduced to a deterministic exit code.

Safe cleanup

Cleanup begins only after the merge commit is proven on the remote trunk. From another checkout, resolve the exact secondary worktree, require an empty Git status, remove it without --force, and verify its folder and registration are absent.

Branch retention

The worktree is disposable. The local and remote path branch should remain as the online per-step history. Worktree removal and branch deletion are separate decisions.

If cleanup fails after a proven merge: “merge complete; cleanup incomplete.” Leave the directory intact.

09

Human records

Persist judgement without pretending to automate it

Cairn turns an acceptance or architectural read into an inspectable file, then limits the checker to facts that file can honestly support.

Ceremony identity

path: CP-EXAMPLE-001
ceremony: closing

The two fields are root-level and matched exactly. A filename remains a navigation aid; metadata defines the proposition. The opening and closing records contain the decision, responses, amendments, and remaining direction in human-readable Markdown.

Architecture decisions

Accepted doctrine belongs in docs/architecture/. A change to that doctrine should carry an ADR in docs/adr/. A coding path executes accepted architecture; it must not hide a new architectural decision only in its ledger.

Journal entry

At merge time, the path creates one entry under project/log/YYYY-MM-DD-<path-id>.md. It names the integrated outcome and links to the path, closing record, audit, and decisions. One path writes one file, so parallel merges do not append to the same document.

10

Enforcement model

Block only on objective repository facts

Blocking

Non-zero exit

The condition is objective and its violation leaves the repository mechanically wrong.

Advisory

Visible signal

The finding may involve judgement, preference, age, likely scope, or an incomplete observer.

Human

Recorded decision

A person or agent judges; automation checks only identity, existence, binding, and minimum completeness.

A rule may block only when the condition is objectively checkable and violating it leaves the repository in a mechanically wrong state.

Three enforcement tiers

TierInstalled mechanismHonest claim
localLocal command onlyThe checker reports; no host is required.
ciWorkflow on trunk and path/**CI observes and publishes; a direct merge may bypass it.
protectedHost requires the CI checksThe host prevents a failing change from merging.

Only local is required. The checker prints the configured tier so documentation never claims prevention when the host only observes.

Mechanical input boundary

The checker may use Git refs and ancestry, filesystem paths, frontmatter fields, changed-file sets, globs, exit codes, declared host variables, and wall-clock age for advisory notices. A non-deterministic model verdict must not control a blocking exit.

Unknown is not success

If a guarded rule cannot identify the subject it must report that condition instead of silently skipping. When missing information is legitimate, unknown stays unknown: an unresolvable branch is neither stale nor fresh.

Executable documentation

Derived facts should be generated. Published templates should be parsed by tests. The detailed rule table in the Markdown source is generated from the checker and compared by the test suite.

12

Guarantees and limits

State the strongest supported fact — no more, no less

What conformance gives you

  • Every implementation belongs to an accepted, bounded path.
  • Every running path is visible from the trunk before its branch diverges.
  • Parallel writers do not share a working directory.
  • Every completed step has local and remote Git recovery points.
  • Every session can resume from durable repository state.
  • Owner acceptance is recorded at opening and closing.
  • Integration begins only from a path containing the current trunk tip.
  • Mechanical facts and human judgements remain visibly distinct.
  • Portfolio views derive from path-owned records.
  • Merge verification and local cleanup end with explicit outcomes.

What Cairn does not prove

Boundary of evidence
  • that an acceptance was wise or an audit conclusion was correct;
  • that checkpoint prose is accurate merely because its file changed;
  • that a recorded base commit describes the intended moment unless explicitly validated;
  • that every commit was pushed immediately — the final graph cannot reconstruct push cadence;
  • that a deleted worktree was clean after repository CI can no longer observe it;
  • that a green test suite covers a behaviour nobody thought to test.

These are boundaries, not hidden promises. Cairn records the strongest fact its inputs support and leaves judgement visible where judgement remains.

Foundation and reference library

Git and project history

A repository is a project folder plus a Git history database. Git saves the project as linked snapshots called commits, not as a pile of renamed copies.

Commit and hash

A commit stores every tracked file, a message, metadata, and a link to its parent. Its identifier is computed from that material, so one short id identifies both the snapshot and the history behind it.

a1b2c3d ──► d4e5f6a ──► 7a8b9c0
  setup        parse         display

Branch and trunk

A branch is a movable name pointing at one commit. The shared main branch is the trunk. Cairn gives each path its own branch, conventionally path/<id>.

Remote and push

A commit exists on the current machine. A remote is another reachable copy of the repository. Pushing creates the remote recovery point Cairn requires before a step is complete.

Merge, conflict, and rebase

A merge combines two histories. A conflict is Git refusing to guess when both sides changed the same region. A rebase replays path commits on top of a newer trunk, producing new ids; Cairn uses it to ensure the path contains the current trunk before self-merge.

Worktree

A worktree is a second working directory for another branch of the same repository. It isolates live files and uncommitted changes. Runtime ports, profiles, caches, and databases may still need their own identity.

Durable project state

Code describes machine behaviour. It does not automatically preserve why a choice was made, what is partly complete, or what the next session must do. Cairn puts those answers in version-controlled files.

Three planes

knowledge plane         architecture, decisions, module notes
execution-state plane   paths, ledgers, sessions, audits, briefs
ephemeral context       one conversation or running process

Three authority shapes

Canonical files are intentionally edited when their represented state changes. Generated views are rebuilt from canonical inputs and never repaired independently. Disposable projections, such as handoff briefs, accelerate reading but can always be recreated from the ledger.

Durable is not true

Git proves that text was recorded in a snapshot. It does not prove the text is accurate. Tests, evidence, review, and later correction still decide that. Cairn never promotes file existence into a semantic guarantee it cannot support.

Progressive disclosure

AGENTS.md
  → project/index.md
  → active path
  → one path ledger
  → only the governing documents it names

Metadata and records

Markdown remains readable as plain text. Frontmatter adds a small machine-readable block at the start:

---
type: Cairn Session Record
title: CP-EXAMPLE-001 closing ceremony
path: CP-EXAMPLE-001
ceremony: closing
---

Schema, not style

A schema defines field locations and allowed values. Root-level path: and ceremony: are part of the ceremony contract. Exact matching prevents one path id from satisfying a record about another.

Judgement becomes an artifact

“The owner accepts this” cannot be recomputed by a script. “A record for this exact path declares the acceptance” can. Cairn checks the latter and leaves the quality of the former to people.

Executable documentation

A published template should be parsed by a test. A published table that can be derived should be generated. This makes the documentation and implementation fail together instead of drifting silently.

Tests, automation, and gates

Test

A test runs code and checks an expected answer. A regression test preserves an identified behaviour or edge case. A green suite means every implemented check passed; it does not cover cases nobody thought to express.

Exit code

0       success
nonzero failure or another exceptional outcome

Automation uses this integer as the verdict. A shell pipeline may expose the final filter's code rather than the check's, so Cairn gates run directly before output is filtered.

Continuous integration

CI checks out the repository in a clean environment and runs the checks for relevant changes. This tests reproducibility and removes “remember to run it” from the workflow.

Blocking and advisory

A blocking finding changes the exit code and must be objectively checkable. An advisory finding stays visible without stopping work. Importance does not decide the tier; the strength of evidence does.

Deployment tiers

local       checker runs without a host
ci          remote runner publishes the verdict
protected   host requires the verdict before merge

Parallel work by structure

Branches isolate committed histories. Worktrees isolate live files. Runtime identities isolate mutable ports, profiles, caches, and databases.

The shared-summary trap

Two writers can update different lines of one status file and Git can merge both edits cleanly into a summary that contradicts itself. No syntax or conflict detector can recognize that cross-line semantic failure.

Generate or partition

Cairn generates aggregate views from path-owned declarations. For append-oriented records it partitions the namespace: one journal entry, audit, session record, or rolled step per owning path.

Register identity before divergence

A checkout cannot scan files that exist only on sibling branches. The stable path tuple is published on the common trunk before its implementation branch exists, so every checkout can discover the work.

Order only integration

Paths work in parallel. They merge in sequence because each next path rebases on the newest trunk and reruns its checks. Seconds of integration are serial; days of work are not.

How the coherence audit stays honest

Architectural coherence matters, but it is a judgement rather than a stable function of bytes. Cairn splits the activity from the deterministic check around it.

reviewer or agent
  reads the rebased diff + architecture + ADRs + coverage
  → writes a path-and-commit-bound judgement

checker
  verifies identity + binding + outcome + substantive answer
  → never decides whether the conclusion is wise

Why the verdict is advisory

A blocking model verdict could vary between runs, require credentials, and prevent legitimate work without a mechanical repair. A filled audit is still valuable: it makes the judgement inspectable and gives the owner a concrete finding to challenge.

Minimum record

  • exact path and branch;
  • a commit from that path's own work;
  • an allowed outcome;
  • at least one substantive response to the audit prompts.

Cairn operations

Register

git switch main
npm run cairn-active
npm run cairn-check
git add project/coding-paths/CP-EXAMPLE-001.md
git add project/coding-paths/ACTIVE.md
git add project/sessions/YYYY-MM-DD-cp-example-001-opening.md
git commit -m "Register CP-EXAMPLE-001 before branching"
git push origin main

Complete a step

npm run cairn-check
npm run typecheck && npm test && npm run build
git add <explicit work-unit paths>
git commit -m "CP-EXAMPLE-001 S01: coherent outcome"
git push origin path/cp-example-001

Rebase and self-merge

git fetch origin main
git rebase origin/main
npm run cairn-check -- --base origin/main
npm run typecheck && npm test && npm run build
npm run cairn-audit
# fill audit, set status: done, commit and push
git switch main
git merge --no-ff path/cp-example-001
git push origin main

Verify and remove

git fetch origin main
git merge-base --is-ancestor <merge> origin/main
git worktree list --porcelain
git -C /exact/path status --porcelain=v1
git worktree remove /exact/path
test ! -e /exact/path
