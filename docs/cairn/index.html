A working protocol for small teams

Cairn.

A project's memory lives in its repository — not in a chat thread, a tracker, or one person's head. Cairn is the set of files that hold it, and the pipeline that checks nobody skipped them.

What it is

Documents delivered at day one, then kept honest

A cairn is a stack of stones left on a trail so whoever comes next knows the route. This one is a small set of Markdown files, dropped into a repo at initialization, that do four jobs.

Everything is plain text under version control. Nothing depends on a specific AI assistant, IDE, or vendor — tool-specific files are pointers to the real documents, never the documents themselves. That is what lets the same project be picked up on another workstation, by another person, or by a different assistant, without a handover call.

Initializes

A one-page bootloader tells any newcomer — human or machine — which three files to read first, and in what order.

Journals

One entry per piece of integrated work. Not commit messages: a narrative of what changed and why, readable a year later.

Documents

Architecture, accepted decisions, and a contract note per module. Written in the same work unit as the code, or the work isn't done.

Manages

A path per feature, broken into numbered steps, each carrying a durable checkpoint: what changed, test state, next action.

Who does what

Three roles, deliberately separated

Most process arguments are really role confusion. Cairn splits the three jobs that get fused in small teams, and the split is the thing that makes it assignable.

Decides scope
Product owner
Opens a path, confirms feature by feature what it will contain before work starts, and accepts it at the end. Owns priority and sequencing.
Does not decide when code merges.
Owns coherence
Integrator
A rotating role, held for a week or a batch of merges. Owns the merge, the journal entry, and the handful of files that can only have one author. Keeps the trunk green.
Does not decide what ships, and is not the reviewer.
Executes
Lane worker
One person or one agent, on one branch, working one path a step at a time — updating code, tests, docs and the checkpoint together.
Does not write the shared coordination files.
Why the integrator isn't just "whoever merges"

In trunk-based development everyone merges their own work, and that is fine when the only shared artifact is code. It stops working the moment a project keeps durable narrative — a journal, a status pointer, a decision log. Those have no merge semantics, so somebody has to own producing the merged truth. If the role can only be done by one specific person, the protocol has failed: it must be executable from the repository alone, which is exactly what the checkpoints and the gate checklist are for.

How work moves

One parent, N lanes, one gate

A single integration parent holds the current direction. Beneath it, any number of lanes run in parallel — one branch and one working copy each. Everything converges through a single gate before it reaches the trunk.

  • 1Lanes stay short. Two days, or it splits. Merge pain is almost entirely a function of branch age — this one rule does more than every other rule here combined.
  • 2One writer per working copy, one active writer per branch. Three workstations are fine; the same branch advanced from two of them is not.
  • 3A lane declares what it expects to touch — as a signal, never a lock. A root cause is discovered, not declared, so the declaration is compared at the gate and reported, not enforced.
  • 4Feedback from real use preempts the plan. A reproduced problem integrates as soon as it is green; longer lanes rebase onto it.
  • 5Rollback is reverting the merge. The lane reopens with its checkpoint intact, and nobody debugs on the trunk.

The idea worth stealing

Statements of record

A few files in any project describe the whole: what's active now, a status register, the journal. It is tempting to declare them unmergeable and lock them. We tried, then ran the merges to check — and mostly, we were wrong.

Four merges, actually run, on the files we were about to lock
Two lanes both…Git's resultCorrect?
append to the journalconflict, visibleyes — keep both, seconds of work
edit adjacent table rowsconflict, visibleyes — trivially resolved
edit distant table rowsclean mergeyes — both edits applied
one closes the parent, one adds a laneclean mergeno — silently contradictory

Three of the four are fine. Git raises a visible conflict, or merges correctly. Only the last fails, and it fails in a specific shape worth naming: a cross-line contradiction, where both edits are individually right and jointly incoherent — the parent marked closed while lanes still run beneath it.

The reason these files have one author isn't that Git can't merge them. It's that nobody checked the claim.

Two lanes writing the status register means two people each asserting what the project's state is, neither having seen the other's work. That's a review concern, not a merge concern — so it earns a warning the integrator reads, not a failed build.

The journal was briefly an exception, on the argument that a lane writing it records work as integrated before it is. That argument doesn't survive: it's circular — the entry is only "wrong" against our own definition of the file — and no untrue statement ever reaches the trunk, because the entry becomes visible exactly when it merges. It's a warning too.

A rule may fail a build when it is objectively checkable and breaking it leaves something wrong in the repository — not merely unconventional.

The instinct: lock it

Declare the file off-limits to everyone but the integrator, and fail the build when a lane touches it.

  • enforces a rule that testing doesn't support
  • blocks work Git would have handled
  • teaches people to route around the check

The better answer: derive it

Generate the section from the files it describes. Each lane's plan already declares its own branch, kind and status — so the list of active lanes is a projection, not a source.

  • nothing to merge, so nothing to lock
  • the contradiction becomes impossible, not forbidden
  • staleness is objective, and the fix is one command

Enforcement

A pipeline check, not a culture

Every rule above can be politely ignored. That's the difference between a habit and a process — so the mechanical half is a script that runs on every pull request, beside the ordinary build.

Two separate jobs, because they answer two different questions and the team needs to see which one failed: does the software work, and was the protocol followed.

What the protocol check verifies on each pull request
LevelCheckFails when

AdvisoryStale contractan area's code changed but its contract note didn't
AdvisoryDecision driftarchitecture changed with no decision record beside it

A false blocking verdict costs more than a missed one — it teaches people to bypass the check.

That isn't theory. The first run of our own checker reported thirty-four broken links that weren't broken: architecture pages illustrating a folder layout inside code blocks. Judgment calls belong in the advisory tier, where a human reads them and nothing is blocked.

Keep the checker dependency-free and free of any AI in the loop. It should run under a bare language runtime in any pipeline, and a sceptical engineer should be able to read the whole thing in one sitting. The command CI runs is the command you run locally.

npm run cairn-check                  # the working copy
npm run cairn-check -- --base main   # a branch, as CI sees it

For whoever runs the project

It maps onto words you already use

None of this asks a product owner or a project manager to learn a new vocabulary. It renames things they already track, and puts them where they can be read without asking anyone.

The honest limit: Cairn carries no estimates, no dates, and no capacity. It is not a replacement for your tracker. The tracker owns priority and scheduling; the repository owns execution state. Decide which wins where on day one, or you get two sources of truth and the team stops trusting both.

Before you adopt it

When not to use this

For one person on a two-week proof of concept, most of this is overhead. The parts that still earn their place at that size are the journal and the decision record — because the thing that actually kills a POC is nobody remembering, three months later, why it was built that way.

Add the rest when a second concurrent writer appears. That's the real trigger: not team size, not project length, but the first moment two people or two agents are changing the same repository at once. Adopting it earlier buys ceremony you can't use yet.

And be suspicious of any rule here you cannot express as a check. It is either a judgment call — in which case say so and put it in the advisory tier — or it is decoration, and it should be deleted.

Adopting it in an afternoon

  • 1Drop in the bootloader, an architecture page, an empty journal, and one plan template.
  • 2Find your statements of record — usually three or four. Derive the ones you can generate; give the rest one author and a warning, not a lock.
  • 3Write the checker for the three rules you'd actually enforce. Add more only when one gets broken.
  • 4Run two lanes for one week, then write down what actually hurt — and only then turn it into policy.
