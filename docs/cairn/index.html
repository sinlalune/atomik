A working protocol for small teams

Cairn.

A project's memory lives in its repository — not in a chat thread, a tracker, or one person's head. Cairn is the set of files that hold it, and the pipeline that checks nobody skipped them.

What it is

Documents delivered at day one, then kept honest

A cairn is a stack of stones left on a trail so whoever comes next knows the route. This one is a small set of Markdown files, dropped into a repo at initialization, that do four jobs.

Everything is plain text under version control. Nothing depends on a specific AI assistant, IDE, or vendor — tool-specific files are pointers to the real documents, never the documents themselves. That is what lets the same project be picked up on another workstation, by another person, or by a different assistant, without a handover call.

Initializes

A one-page bootloader tells any newcomer — human or machine — which three files to read first, and in what order.

Journals

One entry per piece of integrated work. Not commit messages: a narrative of what changed and why, readable a year later.

Documents

Architecture, accepted decisions, and a contract note per module. Written in the same work unit as the code, or the work isn't done.

Manages

A path per feature, broken into numbered steps, each carrying a durable checkpoint: what changed, test state, next action.

Who does what

Two roles, and the job the third one used to do

An earlier version of this page described three roles, the middle one being an integrator who owned the merge, the journal, and the files that could only have one author. The owner of the project this protocol came from rejected that outright: every workstation should be able to merge. He was right, and for a second reason that only showed up afterwards — the integrator had quietly created two of the four gaps an audit later found. Nothing marked work integrated, and the merge gate left no artifact.

Decides scope
Product owner
Opens a path, confirms feature by feature what it will contain before work starts, and accepts it at the end. Owns priority and sequencing. Both conversations are recorded as files.
Does not decide when code merges.
Executes and merges
Path writer
One person or one agent, one path, one branch, one working copy — advancing a step at a time, updating code, tests, docs and the checkpoint together, and merging its own work once the gates are green.
Does not wait for anyone to let it land.
Owns coherence
Nobody — by construction
The integrator's work was split three ways: shared files are derived so they cannot contradict, the mechanical rules are a script the pipeline runs, and architectural drift is read by an agent whose findings inform and never block.
Not a rotating duty, not a person to schedule.
Why removing the integrator made the record better, not worse

The role existed because a project keeping durable narrative — a journal, a status pointer, a decision log — has artifacts with no merge semantics, so somebody had to produce the merged truth. But a human owning that is how it goes stale: the status said one thing, the branches said another, and only the human knew which was true.

Deriving those files from the plans they describe removes the contradiction rather than assigning it. And a path that merges itself sets its own status to done in the very change that lands it, so status and history cannot disagree — the two gaps the integrator had created close by construction, not by discipline.

How work moves

N paths, each merging itself

Any number of paths run at the same time — one branch and one working copy each, one writer apiece. There is no parent above them and no queue of people below them. Each one lands its own work when its own gates are green.

What makes that safe is a single serialized moment: before merging, a branch must contain the current trunk tip. That serializes the merge — seconds — without serializing the work. Two paths can run for two days in parallel and still land safely, because whoever merges second rebases and re-runs the checks.

  • 1The path is registered on the trunk before its branch exists. One tiny metadata-only commit — the plan and the regenerated view of what is running. Skip it and the trunk cannot see the path at all: derived views are only complete if their inputs are global.
  • 2One writer per working copy. Several workstations are fine; the same branch advanced from two of them is not. Every path gets its own worktree, so the owner can keep using the trunk while agents work.
  • 3Every commit is pushed immediately. A step is not complete until it is online, which makes each completed step a safe place to end a session and start a fresh one somewhere else.
  • 4A path declares what it expects to touch — a signal, never a lock. A root cause is discovered, not declared, so the declaration is compared against the diff and reported, not enforced.
  • 5Feedback from real use preempts the plan. A reproduced problem opens a short path and integrates as soon as its checks are green; longer paths rebase onto it at their next step.
  • 6The branch outlives the working copy. After the merge is verified on the remote trunk, the path's checkout is removed — clean, never forced, never the owner's. The branch stays as history.

The idea worth stealing

Statements of record

A few files in any project describe the whole: what's active now, a status register, the journal. It is tempting to declare them unmergeable and lock them. We tried, then ran the merges to check — and mostly, we were wrong.

Four merges, actually run, on the files we were about to lock
Two paths both…Git's resultCorrect?
append to the journalconflict, visibleyes — keep both, seconds of work
edit adjacent table rowsconflict, visibleyes — trivially resolved
edit distant table rowsclean mergeyes — both edits applied
one marks the plan done, one adds a pathclean mergeno — silently contradictory

Three of the four are fine. Git raises a visible conflict, or merges correctly. Only the last fails, and it fails in a specific shape worth naming: a cross-line contradiction, where both edits are individually right and jointly incoherent — a summary declaring the work finished while a new path is being added to it.

The reason these files have one author isn't that Git can't merge them. It's that nobody checked the claim.

Two paths writing the status register means two writers each asserting what the project's state is, neither having seen the other's work. That's a review concern, not a merge concern — so it earns a warning a human reads, not a failed build.

The journal was briefly an exception, on the argument that a path writing it records work as integrated before it is. That argument doesn't survive: it's circular — the entry is only "wrong" against our own definition of the file — and no untrue statement ever reaches the trunk, because the entry becomes visible exactly when it merges. It's a warning too.

A rule may fail a build when it is objectively checkable and breaking it leaves something wrong in the repository — not merely unconventional.

The instinct: lock it

Declare the file off-limits to everyone but one owner, and fail the build when anyone else touches it.

  • enforces a rule that testing doesn't support
  • blocks work Git would have handled
  • teaches people to route around the check

The better answer: derive it

Generate the section from the files it describes. Each path's plan already declares its own branch and status on the trunk — so the list of running paths is a projection, not a source. The journal took the same medicine in a different shape: one file per entry, because two paths writing two files never conflict.

  • nothing to merge, so nothing to lock
  • the contradiction becomes impossible, not forbidden
  • staleness is objective, and the fix is one command

Enforcement

A pipeline check, not a culture

Every rule above can be politely ignored. That's the difference between a habit and a process — so the mechanical half is a script that runs on every pull request, beside the ordinary build.

Two separate jobs, because they answer two different questions and the team needs to see which one failed: does the software work, and was the protocol followed.

A false blocking verdict costs more than a missed one — it teaches people to bypass the check.

That isn't theory. The first run of our own checker reported thirty-four broken links that weren't broken: architecture pages illustrating a folder layout inside code blocks. Judgment calls belong in the advisory tier, where a human reads them and nothing is blocked.

Keep the checker dependency-free and free of any AI in the loop. It should run under a bare language runtime in any pipeline, and a sceptical engineer should be able to read the whole thing in one sitting. The command CI runs is the command you run locally.

npm run cairn-check                  # the working copy
npm run cairn-check -- --base main   # a branch, as CI sees it

Adoption needs only that command. Enforcement comes in three tiers, and only the first is part of the protocol: run it locally (no host, no account); add a CI job, where it observes — a local merge still bypasses it; or configure a rule on the trunk, where it prevents. The third is a property of one repository, never a requirement, and a page that claims prevention it hasn't installed is the same defect as a rule that certifies what it never checked.

For whoever runs the project

None of this asks a product owner or a project manager to learn a new vocabulary. It renames things they already track, and puts them where they can be read without asking anyone.

The honest limit: Cairn carries no estimates, no dates, and no capacity. It is not a replacement for your tracker. The tracker owns priority and scheduling; the repository owns execution state. Decide which wins where on day one, or you get two sources of truth and the team stops trusting both.

Before you adopt it

When not to use this

For one person on a two-week proof of concept, most of this is overhead. The parts that still earn their place at that size are the journal and the decision record — because the thing that actually kills a POC is nobody remembering, three months later, why it was built that way.

Add the rest when a second concurrent writer appears. That's the real trigger: not team size, not project length, but the first moment two people or two agents are changing the same repository at once. Adopting it earlier buys ceremony you can't use yet.

And be suspicious of any rule here you cannot express as a check. It is either a judgment call — in which case say so and put it in the advisory tier — or it is decoration, and it should be deleted.

Adopting it in an afternoon

  • 1Drop in the bootloader, an architecture page, an empty journal, and one plan template.
  • 2Find your statements of record — usually three or four. Derive the ones you can generate; give the rest one author and a warning, not a lock.
  • 3Write the checker for the three rules you'd actually enforce. Add more only when one gets broken.
  • 4Run two paths for one week, then write down what actually hurt — and only then turn it into policy.
