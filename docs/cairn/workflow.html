A working framework, day to day

Running Cairn

From an empty repository to shipped work: who acts at each moment, what the agent does, where a human is genuinely needed, and which file holds the answer afterwards.

How to read this

Each level is complete on its own

Highlighted phrases expand into blocks of the same colour. The rule for the writing, not just the interface: every block opens with a single sentence that is true and sufficient by itself. Opening one of its parts gives you another such sentence, one grain finer — never a continuation of the last.
So you can stop at any level and have a whole answer rather than half of one. Colour tells you , not how deep you are.
Agent · the four actors
Cairn has three actors and one substrate: a human decides, an agent executes, automation checks, and files remember.
Human — appears at exactly two mandatory moments per piece of work, plus whenever they use the product and something rubs. Agent — does the work: reads, writes code, writes documentation, updates the checkpoint. Automated — build gates and the protocol check; no judgment, only verdicts. Artifact — the files, which are the only thing that persists.
A human can do any agent step by hand; nothing here assumes an AI. The division is about when a decision needs a person, not about who types.

The shape of it

The project remembers, not the people

Cairn is a set of Markdown files in the repository holding what was decided, what is being done, where it stands, and what happened. Several people or agents work in parallel, each on their own branch, and each merges their own work.
Three properties make the daily loop below work at all: work is , nothing is , and rather than by goodwill.
Artifact · the path
A path is one file describing one bounded piece of work: what it changes, in what order, and exactly where it stands right now.
It carries numbered steps, a list of documents it must respect (and the ones it is deliberately ignoring, with reasons), and a . Numbered paths come from the roadmap; labelled paths are named for their subject — a repair, a spike, a polish pass.
Artifact · the checkpoint
The checkpoint is the five facts that let a stranger continue the work tomorrow.
base commit : 70f7e27
changed     : electron-main/lane.ts (new), tests/lane.test.ts
tests       : 773/64 pass — typecheck, build, protocol green
remote      : origin/path/cp-ops-001 contains the step commit
session     : safe boundary; fresh session may start at next action
next action : split the module note per area
blockers    : none
Rewritten at every step. It is why three workstations work: pull, read five lines, continue. It is also why an interrupted agent session costs nothing — the context window was never the memory.
Artifact · unshared by construction
The files everyone used to touch are now either generated from the paths, or split one-file-per-entry — so two workers never edit the same thing.
Was sharedNow
what's runninggenerated from the path files
status registergenerated from the same source
the journalone file per entry
module docsone note per area + generated index
This is what removes the need for a gatekeeper. Nobody arbitrates because there is nothing left to arbitrate.
Automated · the split that keeps checks alive
Rules that leave the repository objectively wrong fail the build; everything requiring judgment only speaks up.
Blocking — branch has a path · trunk registration · rebase gate · ceremony recorded · code and docs in one commit · metadata parses · links resolve · generated views current. Advisory — coherence audit · unpublished remote checkpoint · scope drift · stale contract note · decision drift.
A false blocking verdict costs more than a missed one — it teaches people to route around the check, after which it catches nothing.

The daily loop

Nine stages, start to finish

This is the whole framework in use. Each stage names who acts, what gets produced, and what goes wrong if it is skipped.
00

Initialize the repository

HUMANAGENT
Once per project. The document kit lands: a one-page bootloader, an architecture document, an empty decision log, an empty journal directory, a path template, and the protocol check with its pipeline job.
The bootloader is the only file anyone needs to know about — it says . Every AI tool's own config file is a single line pointing at it.
Artifact · the bootloader
One page that points and does not explain, so it can never go stale in a way that matters.
1. this file
2. what's running now      → the generated view
3. the architecture doc    → if this is your first session

Absolute rules that survive a truncated read:
- no work outside an accepted path
- every step: code + tests + docs + checkpoint, one commit
- every commit: push immediately; no push means not complete
- every completed step: agent offers a fresh session
- progress persists in files, never in a conversation
Keep it under a page. The moment it starts containing knowledge instead of pointing at it, it becomes a second source of truth.
produces the kit · skip it and every session starts by guessing
01

Decide what to work on

HUMAN
Two sources, and they are not equal: the roadmap produces numbered paths in sequence, and using the product produces labelled paths whenever something rubs. .
Human · friction preempts the plan
A reproduced problem in what people are actually using integrates as soon as it is green; longer paths rebase onto it.
The alternative — queueing repairs behind roadmap milestones — means the product you use daily stays broken for weeks while the plan advances. The plan is a guess; the friction is evidence.
In practice this means the person using the product files short labelled paths continuously, and the roadmap path absorbs them at its next step boundary.
produces a decision · skip it and work starts without anyone having chosen it
02

Opening check

HUMANAGENT
The first of two mandatory conversations. The agent drafts what it believes the work is, then walks the human through it before anything is written. Corrections amend the draft before it is accepted.
Human · what the conversation looks like
One short prompted confirmation per major feature — "this is what I am about to build, this way; still what you want?" — never an essay to review.
Short options, answered in a word. The answers are recorded verbatim in a session note, because a paraphrase of a decision is a new decision. Activation needs explicit acceptance, not silence.
This is the cheapest moment in the whole loop to change direction. Everything after it costs code.
produces a session note · skip it and you find out at the end that the wrong thing was built
03

Open the path and its worktree

AGENT
The agent writes the path file — id, status, base commit, branch, and the — and lands that accepted declaration plus the generated running-path view in a metadata-only trunk commit. It then creates a separate working copy from that registration so every branch can see that the path exists.
Artifact · declared writes
A declaration of expected reach — an overlap signal when the path opens and a comparison at merge time, never a lock.
Locks fail here because a root cause is discovered, not declared. A bug reported as "labels show file names" turned out to live in the title-resolution helper, and fixing it correctly rewrote four surfaces at once. A convention that forbids what debugging requires gets ignored rather than followed.
Declare documentation surfaces too — those are the ones that actually collide.
git worktree add ../proj-cp-mvp-010 -b path/cp-mvp-010 master
cd ../proj-cp-mvp-010 && ln -s ../proj/node_modules node_modules
produces the path file, a branch, a working copy · skip it and two workers collide in one directory
04

Execute one step

AGENT
The repeating unit, and the heart of the framework. One step means: change the code, change the tests, , update the checkpoint and the path's rolling handoff brief — . Run the gates locally, bare, then push immediately.
Agent · what documentation means here
Three kinds, each triggered by a different thing, and none of them optional.
The module note — one per area of the system, stating what that area owns and the contracts it exposes. Updated whenever its code changes. The learning note — written the first time the project uses a technology or pattern, explaining it to someone who did not build it. The decision record — written when an architectural choice is made, with the alternatives considered.
And a fourth, which most projects skip: .
Agent · the figure
Every module note carries a figure of what it owns, and every path introducing a new mechanism ships a drawing of that mechanism in the same commit.
Prose is bad at three specific things, and those three are exactly what a newcomer needs first: what talks to what, what happens in what order, and where the trust boundaries are. A paragraph describing a five-step pipeline takes longer to read than the pipeline takes to run.
The section further down says what to draw and how to keep it honest.
Agent · why one commit
Anything left for later drifts immediately, so "done" is defined as all four landing together.
This is one of the few rules a pipeline can check mechanically — source changed, so a module note and a checkpoint must have changed too — which is why it is enforced rather than encouraged. It also makes "done" stop being a judgment call: either the commit contains all four or it does not.
Gates run bare: the exit code is the verdict, never a grep over the output. A pipe once swallowed a failing type-check and shipped a white screen.
The commit is pushed before completion is reported. Once it is online, the agent proactively offers to execute the recorded next action in a fresh session. The path stays open; only the chat ends, and the owner supplies no recap.
produces a pushed commit, checkpoint and fresh-session boundary · skip parts and the docs describe a system that no longer exists
05

Bench round

HUMANAGENT
Optional, and in practice the highest-value hour in the week. The human uses what was just built and says what is wrong, in their own words. The agent .
Agent · absorbing a report
Pin the exact state, reproduce it, add the regression test, then fix — in that order, always.
Pin means: the commit, the data, the configuration. A report compared against an unpinned state is an opinion about two different systems. Reproduce before fixing, because a fix without a reproduction is a guess that happens to change the symptom.
The report's own words go into the record verbatim. "Design issue, also why need separation when expanded?" is more useful six months later than a tidy paraphrase, because it preserves what actually bothered someone.
produces steps, regression tests, sometimes a new path · skip it and the work is only correct against its own assumptions
06

Every commit is pushed — the pipeline answers two questions

AGENTAUTOMATED
The push is the remote recovery point and adds a GitHub Activity event separate from the commit's own timestamp. With an open pull request—or on a trunk push—the configured workflow starts two deliberately separate jobs, because a red build and a broken protocol need different fixes: does the software work (type-check, tests, build) and was the protocol followed (the check, including ).
Automated · the rebase gate
A branch must already contain the tip of the trunk before it may merge — which serializes merging without serializing work.
This is the mechanism that makes a gatekeeper unnecessary. Two paths run for two days in parallel; whoever merges second pays a rebase and a re-run, which takes minutes. With a human gatekeeper, every merge instead waits on one person's attention.
The re-run matters as much as the rebase: CI must be green on the rebased result, not on a stale branch that was green against a trunk that has since moved.
produces an online checkpoint and two verdicts · skip it and the next session depends on this machine
07

Closing ceremony

HUMANAGENT
The second mandatory conversation, and the last human judgment before the work lands. The agent presents a , the human accepts the work, and together they decide what comes next.
Agent · recall from files, never from memory
Everything presented at the ceremony is read out of the repository — the register, the checkpoints, the journal — never recalled from the conversation.
A conversation-based recall is a summary of a summary, and it quietly omits whatever fell out of the context window. A file-based recall is auditable: the human can open any line of it.
The output is a session note. It is also what the pipeline looks for — a path marked done without one fails the check, because with no gatekeeper this ceremony is the only human guard left.
produces a session note, an accepted path, a decision about what's next
08

The path merges itself

AGENTAUTOMATED
Rebase, let the pipeline run again, record a , set the path's own status to done in the same pull request, merge, and immediately push the trunk. Nobody approves it; the gates already did.
Automated · a deterministic gate on a non-deterministic activity
An agent reads the rebased diff for architectural drift and writes a record; the pipeline checks only that the record exists and is filled.
This replaces the one thing lost by removing a gatekeeper — the person who noticed two parallel efforts pulling in different directions. The questions are fixed: does this contradict an accepted decision, duplicate another running path, introduce architecture with no decision record, or document something in a second place that will drift?
Its verdict never blocks. A pipeline that fails on a model's opinion is unpredictable, expensive, and needs credentials it should not hold. If after some months the audit has never caught something a human would have missed, delete it rather than keep it as decoration.
produces a merge, a journal entry, regenerated views · skip the rebase and two green branches combine into a red trunk
09

Retire the merged worktree

AGENT
From another checkout, verify the exact merge commit on the remote trunk, resolve the path's secondary worktree, and require an empty Git status. Remove that exact checkout with non-forced git worktree remove, then verify its registration and folder are gone. Never target the main/owner or a dirty worktree. Keep the local and remote path branch: folder cleanup is not history deletion.
produces no stale completed checkout and retained online history · if any proof fails leave the folder intact and report cleanup incomplete

Visual documentation

Draw the implementation, not just the process

Figures are documentation and rot faster than prose, because nothing complains when they go stale. A Cairn project draws four specific things about its own implementation, and audits them like any other document.

What to draw

FigureAnswersLives with
Module mapwhat exists, what owns what, what may call whatthe root module note
Boundary mapwhere the trust and process boundaries are, and what crosses themthe security or architecture doc
Flow of one operationwhat happens in what order when the system does its central thingthe module note that owns it
Lifecyclethe states a core object moves through, and what moves itthe document defining that object
Those four cover what prose is worst at: . Beyond them, a path adds a figure whenever it introduces a mechanism a newcomer would otherwise have to reconstruct from code.
Artifact · why these four
Each of the four answers a question a reader has to hold in their head all at once, which is exactly where sentences fail.
A module map answers "what am I allowed to touch". A boundary map answers "why is this indirection here" — usually the most confusing thing in a codebase, and almost never explained. A flow answers "where does this go wrong". A lifecycle answers "can this state even happen".
If a figure would only restate a paragraph in boxes, it is decoration and should not exist. The test: could a newcomer answer the question faster from the figure than from the text?

The rules that keep them true

  • A figure is a derived view. It draws a mechanism that already exists in a named document; it never introduces structure the written corpus does not contain. If a figure needs a box the documents do not describe, the documents are wrong — fix them first.
  • One mechanism per figure. Detail belongs in the document being projected.
  • A register row per figure — id, file, what it projects, and the trigger that makes it stale.
  • Same commit. Change a projected section and the figure updates with it. A stale figure is a documentation bug, not a cosmetic one.
  • Self-contained, so it renders in code hosting, in exports, and in whatever reader comes next.
  • and are never hand-edited.
Automated · generate, then assert
A figure worth keeping is emitted by a short script that asserts its own geometry — because a hand-placed diagram is a hundred coordinates nobody can review.
Three assertions cover almost everything: no box overlaps another, nothing falls outside the canvas, and every floating label's full text extent clears every box. They are not theoretical — writing them caught two real placement bugs in this project's own figures, the second only because the check measured a label's text extent rather than its anchor point.
Once generated, the script is the source and the image is a build artifact. Editing the image is the same mistake as editing compiled output.

All of it at once

The loop

Colour carries the same meaning as above: ochre where a human is required, violet where the agent works, teal where automation decides.
Where this stands. Cairn is accepted under ADR-012 and has carried multiple paths through self-merge. Its rules continue to change only when real execution exposes a gap.
Known limits remain explicit: abandoned-path lifecycle, base/checkpoint prose accuracy, the fact that local refs cannot prove historical one-push-per-commit cadence, and that repository CI cannot observe post-merge cleanup on a developer's machine.
