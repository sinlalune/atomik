# What defines the protocol

The most lightweight and minimalistic harness agnostic document driven coding protocol.

# The engine

It is built on a OKF norms with three commitments : optimized; distributed and decentralized

The repo architecture needs to be the leaniest :
- No duplicate folders with close missions - the less the better
- The tree hierachy logic needs to be free standing - accessibility by design
- Leave the lightest token footprint trough exploration and navigation

# The brain

At its core the protocol is leveraging a shared (agent/user) concept knowledge base : protocol, project or coding that present abstraction complexity.
We believe that semantic decomposition is best way to learn.

# The chronology :

- You get an idea overnight, instead of coding it right away, you sit on it.
- Through ideation, researches and brainstorms you finetune your vision.
- From that vision you design an MVP and you generate documents of specification : features, architectures, workflow, interface, contracts, etc..
- From that set of document you choose the best projected roadmap to MVP.
- From that roadmap, you build each coding cycle around referenced pre-produced documentation
- During the project, if ideas comes across and you want to explore, you research and document the same way to be referenced in next cycles.

Your focus is on your vision and how it evolves.
The role of the protocol is to not assume that its fixed but invite you to challenge yourself by iteration.

# The approach :

The protocol need to be in symbiosis with modern tools and best practices.
It means to have the fluidest and logical interaction with pre-existing workflows : parallel agentic coding, versioning, CI/CD.

The core idea is : finding the right balance between robustness, stability and simplcity.

If the workflow needs to design non-native solutions of theses workflows then it is mostly probable that it is not a best practice, and we specifically desire to build on those.

# The code

We must provide the most safe and sound coding workflow, inspired by state of the art best practices :
- Sequencing isolated steps : planning, coding, reviewing, tests
- Thinking through an experimented and reflected mind : what is the simpliest and cleanest way to implement it.
- Adapt to constant changes in the global coding ecosystem : observe, assess and absorbs changes that drives progress

# The engagement

Even if the protocol is leveraging production level of tools and worflows, the protocol needs to be accessible on the surface.
We provide a set of documentation to get used to it but meanwhile the interface need to be beginner friendly.

# The pedagogy

The protocol needs to set up a cultural way of sharing through pedagogy.

Every written line in the documentation, in the chat sessions, in the artefacts ; everything that is written or generated needs to be in the intention being effortlessly comprehensible.

# The project

In addition to documentation, the protocol needs to maintain the lightest bust most efficient layer of project context artefacts.
Its mission is to extract the essence of it sufficiently to achieve complete agnostism from previous or future implementation context.

# Main threaths

- Searching for more control in the volume of tests and complexity of workflows
- Assuming that a state of the protocol is definitive and can't be challenge by refactoring and simplification
- Not embracing progresses outside the protocol
- Not respecting the manifesto

# Main opportunities

- Always be open to simplier worlflows
- Always challenge the protocol
- Always provide meaning to what you build
- Always leverage what you built
