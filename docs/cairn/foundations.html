A primer · production software practice, from zero

You already believe in
all of this.

Version control, tests, continuous integration, working protocols — most of it is something you already do, implemented in a different medium and named in a different vocabulary. Here is the translation.

Who this is for

Someone who writes real code, and has never worked inside a production setup

You have trained models, run analyses, and produced figures that went into something that was reviewed. You know what it costs to be wrong, and you have a whole apparatus for not being wrong: controls, held-out data, preregistration, replication, review.

What you may not have is the other apparatus — the one software engineering built for the same purpose, with different words. From the outside it looks like a wall of jargon and ceremony, and the first encounter is usually stressful: everything is unfamiliar, everything seems to be enforced by something that says no, and none of it appears to be about the problem you actually have.

This page is written on the opposite premise.

None of it exists to slow you down. All of it exists so that you can move faster without being afraid — the same way a held-out test set lets you tune aggressively without fooling yourself.

That is the whole emotional content of production engineering, and it is worth saying out loud, because the tooling never says it.

Part 1

The shape of the problem

Here is a situation you have been in.

In May, an analysis worked. There is a figure from it, and the figure is right. It is November, and someone asks you to run it again on the new cohort.

You open the folder. There are four scripts with similar names, two of which end in _final. There is a notebook whose cells were run out of order, so the variable that produced the figure no longer exists in any order you can reconstruct. The package that did the tokenisation has moved to version 4 and changed a default.

You can probably rebuild it. It will take two days, and at the end you will not be certain it is the same analysis.

Nothing about this was an intelligence failure. It is a process failure, and it is the same one the reproducibility crisis is about. Software engineering had its own version — repeatedly, expensively, sometimes with people's money or safety attached — and answered it with a small set of mechanisms that are now so standard they have become invisible to the people using them.

They answer four questions:

What exactly was the state of everything when this worked?   version control
How do I know it still does what it did?                     tests
Who checks that, and when?                                   continuous integration
How do several people do this at once without collisions?    a working protocol

None of them requires you to change what you are researching. They are about the substrate the research sits on.

Part 2

Version control, from zero

The problem it solves

You have solved this already, badly, and so has everyone else:

analysis.py
analysis_v2.py
analysis_v2_fixed.py
analysis_final.py
analysis_final_REALLY.py

That is a version control system. It is a bad one: it cannot tell you what changed between two of those files, why, when, or by whom — and it cannot recover the state of the whole project at the moment one of them was correct, because the data-loading module changed too and was overwritten in place.

Version control is that idea done properly, for a whole directory at once. The dominant one is Git.

A commit

A commit is a complete snapshot of every tracked file at one moment, plus who made it, when, a message saying what it is, and a pointer to the commit it came from. Two things surprise people:

It is a snapshot, not a change. Git stores the whole state and shows you changes by comparing two snapshots — which is why it can diff any two points in history, however far apart.

It has a name you do not choose. Every commit gets an identifier like b4ef361, a hash computed from its content, its metadata, and its parent's identifier. Because the parent's id includes its parent, a commit's id fingerprints the entire history behind it. You cannot quietly alter an old commit and leave the later ones looking untouched. The ids all change, visibly.

In your world

A bound, page-numbered, ink lab notebook. Its value is not convenience — it is that you cannot go back and make yesterday say something else.

→
In software

Git history. The same guarantee, with search and diffing on top, and the tamper-evidence is cryptographic rather than physical.

A commit message is not decoration. The code shows what; the message is the only record of why.

History is a graph

Because every commit points at its parent, history is a chain:

a1b2c3 ──► d4e5f6 ──► 7a8b9c ──► b4ef361
 "load"     "clean"    "model"    "figure"

Check out any of those points and you get the project exactly as it was — all files, consistently, not one file at a time. Commits can also have two parents, which is how two lines of work rejoin, so history is a graph rather than a line.

Branches

A branch is a name pointing at one commit. That is genuinely all it is; when you commit, the name moves forward. The reason it matters is that you can have several, and they can diverge:

                    ┌──► f1a2b3 ──► c4d5e6      branch: try-focal-loss
a1b2c3 ──► d4e5f6 ──┤
                    └──► 9z8y7x                 branch: main
In your world

A parallel experimental arm. You would never test an intervention by overwriting the control group's data and hoping you could reverse it.

→
In software

A branch. Work on one cannot damage the other; if the idea fails you delete it, and even the record that you tried is worth keeping.

One branch is conventionally the shared, agreed, current one — main, master, or the trunk. It is the version of the manuscript everyone agrees is the manuscript.

Merging, and why conflicts are good news

Merging brings one branch's work into another. Git compares both sides against the point where they diverged; if they changed different things, it combines them and records a commit with two parents. If both changed the same lines, Git stops and reports a conflict.

New users experience this as Git being difficult. It is the opposite. Consider the alternative: two people edit the same paragraph in two copies of a Word file, and someone merges them by hand at 11pm. The failure mode there is not an error message — it is a paragraph that reads fine and says something neither author meant. Git refuses to guess.

Remote, and what "done" means

So far everything is on your machine. A remote is a copy of the repository somewhere else — usually a hosting service — that several people can reach. You push commits to it and pull theirs.

The distinction that costs people work: committing is not backing up. A commit lives inside your project folder. If the laptop dies, the commit dies with it. Only a push puts it somewhere else — which is why disciplined teams treat commit-and-push as one action and consider work unfinished until it is on the remote.

Part 3

Tests: the controls you run on your own code

A test is code that runs your code and checks the answer. The smallest possible one is a single line:

assert normalise_dose("5 mg") == 5.0

If that is true, nothing happens. If it is false, the program stops and says so. That is the entire idea; everything else is organisation.

Unit tests, suites, and "green"

A unit test checks one small piece in isolation. A test suite is all of them together, run by one command. It either passes completely — called green — or reports which cases failed and why, which is red.

In your world

A positive control. You do not trust an assay because the protocol was followed; you run a sample whose answer you know, and if that comes out wrong you discard the batch.

→
In software

A test suite. A rack of positive controls that runs in eight seconds, every time, at no cost.

The regression test: a scar that becomes a guardrail

This is the most valuable kind. Something breaks; you find the cause and fix it. Before moving on, you write a test that fails on the old code and passes on the new.

Its job is not to check the fix — you can see the fix works. Its job is to make sure this specific failure can never come back silently, including in two years, when the person who reintroduces it has never heard of you. Every mature codebase is partly a museum of these, and reading them tells you more than the documentation does. It is the cheapest institutional memory that exists: a bug costs you a day once, and then never again.

Test-driven development is preregistration

Test-driven development inverts the order: write the test first, watch it fail, then write the code that makes it pass. Stated coldly it sounds like ritual. Stated in your vocabulary it is obvious.

In your world

Preregistering the analysis. You write down the criterion for success before you have the thing that has to satisfy it, so you cannot unconsciously move the goalposts.

→
In software

Red, green, refactor. Anyone who has written a test after the fact knows the quiet temptation to write the test the existing code already passes.

The third step is undersold. Restructuring code without tests is frightening, so it does not get done, so the code calcifies. With a suite you can rip a module apart at 4pm and know by 4:01 whether you broke anything. That is what tests actually buy: not correctness, but the freedom to change things.

What tests do not prove

A passing suite means "none of the things we thought to check are broken". It does not mean the software is correct, and no amount of testing makes it mean that — a study can be perfectly executed and still be measuring the wrong thing. Tests are necessary, insufficient, and worth every minute. The discipline is to add one whenever you are surprised.

Part 4

Continuous integration: someone else runs the checks

Continuous integration is one idea: every time anyone changes the code, a machine that is not theirs checks out the change and runs the checks.

There is no cleverness in it. Its power is entirely in "not theirs" and "every time".

Not theirs, because your machine has your environment, your half-installed packages, your one file that never got committed. A clean machine that starts from the repository alone is the only honest test of "does this work for anyone other than me". Every time, because a check that runs when someone remembers is a check that does not run.

In your world

Instrument QC that runs before every batch, automatically, whether or not the operator is worried.

→
In software

CI. Not because operators are careless — because reliability is a property of the process, not of anyone's attention.

"It works on my machine"

The commonest cause of a red run on healthy code is the environment. That is not CI being fussy — it has just discovered that the project is not actually reproducible, which was true before anyone noticed. The answers, in increasing strength, are a dependency list, then a lockfile pinning exact versions, then a container holding a whole operating system image. You have met the same ladder as sessionInfo(), then renv, then a container on the cluster.

The gate, and what green means

A gate is a check with authority: something that can stop a change from proceeding. A CI run is a gate only when the project is configured so a red run blocks the merge — otherwise it is a report. Three levels:

SetupWhat it actually does
no checknothing is enforced
check runsCI observes — it reports, and a human may ignore it
check blocksCI prevents — nobody may ignore it

Documentation claiming the third while the project is configured for the second is worse than documentation claiming nothing, because people then rely on a guard that is not there.

A failure this project actually had

For a period, this repository's CI was configured to run only on the trunk and on pull requests — and every merge here has been a local merge commit, so there had never been a pull request. Every rule about branches had therefore never once executed in the place it existed to enforce.

The rules were real. The enforcement was not. And nothing said so, because a check that never runs prints nothing — which is indistinguishable from a check that passes.

A control you never verify is running is not a control.

Why the checks are run bare

Checks are run bare — the command runs and its exit code is the verdict, not piped into anything that filters or reformats the output.

A failure this project actually had

On 2026-07-16 a broken build shipped because a check was piped through grep and head. A pipeline reports the status of its last command, so the failing status was discarded. The program was broken and the gate said green.

Part 5

More than one person

Everything so far works for one person alone. Add a second — or an automated agent — and failure modes appear that no tool detects by itself.

Code review is a second person reading a change before it lands: peer review with a much shorter loop, no anonymity, and a narrower question — not "is this a contribution to the field" but "will this do what it says, and will the next person understand it".

The genuinely hard part is not review. It is shared files. Two people editing different functions never collide. Two people editing the same summary table, the same index, the same "current status" document collide constantly — and worse, sometimes invisibly, where Git merges both edits cleanly and the result is a document that contradicts itself. Each edit was right; the pair is wrong. No tool catches this, because syntactically nothing is wrong.

There are two real answers, and mature projects use both.

Make the shared file generated

If a file is derived from other files by a script, nobody edits it, so nobody collides on it.

In your world

You do not edit a figure in Illustrator. A figure touched by hand after generation no longer matches the data — and the fact that it still looks fine is precisely the danger.

→
In software

A generated file. Same argument, applied to prose: regenerate it, never patch it.

Give each writer their own file

A shared log where everyone appends collides on every line; the same log split into one file per entry never collides at all. That is a concurrency fix, not a size one — a distinction worth keeping straight, because the wrong reason produces the wrong rule later.

Order the moment of combination

If two people work for two days in parallel, the merges must be serialised — for thirty seconds each — even though the work was not. The usual rule: before you merge, incorporate the current trunk into your branch and re-run the checks, so what gets tested is what will actually exist afterwards. One rule, mechanically checkable, and it removes the need for a person whose job is to stand at the door.

Part 6

Why a protocol on top of the tools

Git records changes. Tests check behaviour. CI runs the checks. None of them answers:

Is this work written down anywhere other than in the head of whoever did it?
Did anyone actually accept this before it started?
Is the documentation still true?
Is the reason for this decision recorded, or only its outcome?

A protocol is the agreed set of practices that answers those — plus, and this is what makes it real, the subset a script can check. Cairn is this project's protocol; what follows is the reasoning, which transfers even if you never use Cairn itself.

Work happens inside a declared unit

Nothing is implemented outside an accepted coding path: a small file declaring what is being built, on which branch, from which starting commit, and which files it expects to touch. It carries a work ledger — an append-only record of what each step actually did.

In your world

The methods section, written as the work happens rather than reconstructed at submission. You know how much is lost in reconstruction.

→
In software

The work ledger. The parts most worth having — what did not work, why that parameter, the decision that was reversed — are the first to evaporate.

Ceremonies: the human decisions leave a record

Two moments require a human and produce a written artefact: an opening check before work starts, and a closing ceremony before it merges. Each is recorded in a note whose metadata declares which path it belongs to and which ceremony it is.

A failure this project actually had

An earlier version of the checker looked for a file whose name contained the path's id. But such a file exists from the path's first hour, because the opening note carries the id too.

So the check meant to prove a path had been closed was in fact proving it had been opened — and it passed every time. A check can be running, and green, and testing the wrong proposition entirely.

Blocking and advisory

Every rule is one of two kinds: Blocking fails the build and nothing lands until it is fixed; Advisory prints, a human reads it, and the work continues.

In your world

Hard exclusion criteria versus flags for manual review. You do not treat "unusual" and "invalid" as the same category.

→
In software

Blocking versus advisory — the single most important design decision in the whole protocol.

A rule earns the right to block only if:

it is objectively checkable, and breaking it leaves something wrong in the repository — not merely unconventional.

Undocumented code is wrong. A journal entry written by the person who did the work rather than a reviewer is unconventional. Only the first may fail a build.

The asymmetry underneath is worth internalising: a false blocking verdict costs far more than a missed one. A gate that stops legitimate work teaches people to route around it, and once a team has learned to bypass a control you have lost the control and the information it produced. Every lab has one instrument with a QC threshold everyone knows to override.

A failure this project actually had

The first run of this validator reported 34 broken links that were not broken — they were architecture pages illustrating a folder layout inside code blocks.

Had that been left blocking, the checker would have been switched off within a week, and none of the real rules would exist today.

The parts a machine cannot check, and saying so

Some things that matter are not checkable at all: is this design still coherent with the architecture we agreed on; is this paragraph still true; was this the right thing to build.

The answer is not to pretend. Before a merge, an agent reads the change against the accepted architecture and writes a coherence audit. CI checks only that the record exists and has been filled in; its verdict never blocks. That is a deterministic gate wrapped around a non-deterministic activity, which is the only honest way to automate a judgement. The remaining gaps are written down as open holes rather than quietly omitted — a protocol that names its own blind spots is one you can trust about everything else.

The rule that keeps all of it honest

The failure this project has fought hardest is subtler than any bug:

a published rule the implementation does not honour.

An operator guide prescribing a metadata format the parser rejects. A rule table listing checks that did not exist in code. A page teaching a workflow replaced ten days earlier. In each case the document was confident, the reader was reasonable, and following it produced a failure. The defences are mechanical, and they generalise to any documentation you write:

  • 1Generate what can be generated. The rule table in the specification is produced from the checker's own source, so it cannot describe a rule that does not exist — and a test compares the shipped table against the generator on every run.
  • 2Make the documentation executable. The metadata template published in the standards page is parsed by the test suite, so a template that would not work fails the build.
  • 3Date every page and name what it renders. The page that drifted for ten days drifted unnoticed because nothing on it claimed a vintage. That is why this page has a line at the top.

If you take three things

What to do with all this

  • 1Commit small, message honestly, push immediately. An unfalsifiable record of your own work and a backup, for about ten seconds a day.
  • 2Write a regression test every time something surprises you. The cheapest institutional memory in existence, and it compounds.
  • 3Run the checks on a machine that is not yours, on every change. Everything else in continuous integration is detail.

Everything beyond that is scale. A protocol like Cairn matters when several people or agents work at once, when work spans months, and when the reason for a decision has to survive the person who made it. If you are working alone on something short, the three above are most of the value and you should not feel behind for stopping there.

The point of the apparatus is not compliance. It is that you can change things without being afraid — and that you can leave, come back in a year, and the project will tell you what it is rather than making you remember.

Appendix

Glossary

One line each. The full version, with the precise definition and the file that enforces each term, is docs/cairn/lexicon.md.

General practice

Commit
A saved snapshot of the whole project, with a message and a link to what came before.
Branch
A name for a line of work — a movable pointer to one commit.
Trunk / main / master
The version everyone agrees is current.
Merge
Bringing one branch's work into another.
Conflict
Git refusing to guess when two people changed the same lines. A feature.
Rebase
Replaying your commits as if you had started from a later point. Safe on private work, disruptive on shared work.
Remote
The shared copy, elsewhere. Committing is not backing up; only a push is.
Worktree
A second checkout of the same repository, on another branch, in another directory.
Continuous integration
A machine that is not yours runs the checks on every change.
Gate
A check with the authority to stop something. A check that only reports is not a gate.
Green / red
Everything passed / something failed.
Bare
Run the command and read its exit code — do not pipe it anywhere.
Unit test
A positive control for one function.
Regression test
A scar turned into a guardrail: written when something breaks, so it cannot come back silently.
Test-driven development
Preregistration for code. Write the failing test first.
Lockfile
The exact versions, not just the names, so a clean machine reproduces yours.

Cairn vocabulary

Coding path
One bounded piece of work, declared in a file before it starts. Nothing is implemented outside one.enforced by tools/cairn-check.mjs
Work ledger
The methods section, written as the work happens.enforced by the same-work-unit rule
Opening check
The owner accepting the work before it starts.blocking
Closing ceremony
The owner accepting the result before it merges.blocking
Registration commit
Putting the path on the trunk before its branch exists. Metadata only — no implementation of any kind.blocking
Rebase gate
A branch must contain the current trunk tip before it merges. Serialises the merge without serialising the work.blocking
Self-merge
Every path merges itself. There is no integrator and no gatekeeper.
Coherence audit
An agent reads the change against the accepted architecture before it merges. CI checks that the record exists; the verdict never blocks.advisory
Derived view
A file generated from other files, so nobody edits it and nobody collides on it.blocking on the trunk
Blocking
The build fails; nothing lands until it is fixed.
Advisory
It prints, a human reads it, the work continues. Where every judgement call lives, permanently and by design.
Admission test
What a rule must satisfy to be allowed to block: objectively checkable, and breaking it leaves something wrong in the repository.
Enforcement tier
How much your setup can actually prevent: local, CI observes, or a host ruleset where CI prevents. A property of a repository, never a requirement of the protocol.
Known limit
Something the protocol cannot check, written down rather than omitted. There are two.
